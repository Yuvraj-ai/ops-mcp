# Idempotency Keys Design Spec

## Goal
Make `reconcile_order` and `issue_refund` idempotent: if the agent retries with the same `idempotency_key`, the server returns the stored result instead of re-executing the operation.

## Approach
**Handler-level idempotency** (Approach A): Check the idempotency key at the top of each write-tool handler. If found, replay the stored result. After fresh execution, store the result with the key. Audit logging happens for both fresh and replayed paths.

## Schema Change
New table in `src/db/schema.sql`:

```sql
CREATE TABLE IF NOT EXISTS idempotency_keys (
  tool_name  TEXT NOT NULL,
  key        TEXT NOT NULL,
  result     TEXT NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  PRIMARY KEY (tool_name, key)
);
```

## Repository Changes
Two new methods in `OpsRepository` (`src/db/queries.ts`):

```typescript
async getIdempotencyResult(toolName: string, key: string): Promise<any | undefined> {
  const result = await this.pool.query(
    "SELECT result FROM idempotency_keys WHERE tool_name = $1 AND key = $2",
    [toolName, key]
  );
  if (result.rows.length === 0) return undefined;
  return JSON.parse(result.rows[0].result);
}

async storeIdempotencyResult(toolName: string, key: string, result: any): Promise<void> {
  await this.pool.query(
    "INSERT INTO idempotency_keys (tool_name, key, result) VALUES ($1, $2, $3)",
    [toolName, key, JSON.stringify(result)]
  );
}
```

## Input Schema Changes
Both `reconfirm_order` and `issue_refund` gain a required `idempotency_key` input:

```typescript
idempotency_key: z.string().describe(
  "A UUID generated by the agent for this specific attempt. Reuse on retry to get the same result. Required."
)
```

## Handler Flow (both write tools)

```
1. Check idempotency key → if exists, replay stored result (isReplay = true)
2. If new key → execute handler logic (existing try/catch + validation)
3. Audit log the result (always — both fresh and replayed)
4. Store idempotency key + result (only for fresh, non-replayed executions)
5. Return result
```

Refactored handler structure:
```typescript
handler: async (input: {...}) => {
  let result: any;
  let isReplay = false;

  // Step 1: Idempotency check
  const existing = await repo.getIdempotencyResult("reconfirm_order", input.idempotency_key);
  if (existing) {
    result = existing;
    isReplay = true;
  } else {
    try {
      // ... existing validation + execution logic
    } catch (err) {
      result = { error: err instanceof Error ? err.message : String(err) };
    }
  }

  // Step 3: Audit log (always)
  await repo.logAction({
    order_id: input.order_id,
    tool_name: "reconfirm_order",
    input_json: JSON.stringify(input),
    result_json: JSON.stringify(result),
    success: !("error" in result),
  });

  // Step 4: Store idempotency key (only for fresh executions)
  if (!isReplay) {
    await repo.storeIdempotencyResult("reconfirm_order", input.idempotency_key, result);
  }

  return result;
}
```

## Tool Description Updates
Both write tool descriptions get this guidance appended:
> Generate a fresh UUID for idempotency_key per logical attempt. If you retry after a timeout or error, reuse the SAME key verbatim — the server will replay the stored result instead of re-executing.

Both methods are best-effort: `getIdempotencyResult` catches errors and returns `undefined` (treats as "no key found" → proceeds with fresh execution); `storeIdempotencyResult` catches errors and logs to console (operation already succeeded, key just isn't stored). This ensures idempotency table issues never break write operations.

## Out of Scope
- No TTL/expiration on idempotency keys (noted as production concern in README — Stripe uses 24h)
- No cleanup/deletion mechanism for old keys
